## 1. Tech decisions (one choice per "X or Y" in the synopsis)

| Area | Choice | Why |
|---|---|---|
| Backend | **FastAPI** + Uvicorn | Synopsis lists FastAPI/Flask. FastAPI gives request validation without extra libraries. |
| Database | **SQLite** (stdlib `sqlite3`, plain SQL, no ORM) | The PCAP pipeline has to write SQLite anyway, so one engine and one DB file covers everything. |
| Password hashing | **Argon2id** (`argon2-cffi`) | FR-02 |
| Encryption + hashing | **`cryptography`** (AES-256-GCM) + stdlib `hashlib` (SHA-256) | PyNaCl's high-level API doesn't offer AES-GCM (see issue S1). |
| Frontend | **React + Vite**, plain CSS, `fetch`, no router or UI library | Synopsis names React. A responsive CSS layout covers PC and mobile (FR-18). |
| Client-side hashing | Browser **WebCrypto** (`crypto.subtle.digest`) | Built in and needs no dependency. It gives real post-transfer verification (FR-21). |
| Transport | **HTTPS/TLS** with a self-signed CA generated by a script using `cryptography` | No openssl or mkcert needed. |
| Traffic | **Wireshark** (capture) + **PyShark** (analysis) | G8 and FR-23 to FR-26 |
| Evaluation | `numpy`, `Pillow`, `psutil`, `requests` (eval scripts only, not imported by the server) | Image metrics, CPU and memory, HTTP benchmarks |

**Complete dependency list**
- `backend/requirements.txt`: `fastapi`, `uvicorn`, `python-multipart`, `argon2-cffi`, `cryptography`
- `analysis/requirements.txt`: `pyshark` (plus Wireshark/tshark installed on the machine)
- `evaluation/requirements.txt`: `numpy`, `pillow`, `psutil`, `requests`
- `frontend/package.json`: `react`, `react-dom`, `vite`, `@vitejs/plugin-react`

Explicitly not used: ORM, Docker, Redis, WebSockets, `python-magic`/libmagic, a JWT library, a CSS framework, or pytest. Verification is done with demo scripts and a checklist (section 8).

**Deployment shape:** FastAPI serves the built React app and the API from **one HTTPS origin** (`https://<server-lan-ip>:8443`). That means one certificate, same-origin cookies, and no CORS setup.

## 5. How each function works

### 5.1 Accounts and authentication (FR-01 to FR-03, SR-03)
- There is no register endpoint. `scripts/init_admin.py` creates the first admin, and after that only `POST /api/admin/users` (requires `manage_users`) can create users with name, company profile, department, role, password and status.
- Passwords are hashed with Argon2id. The encoded hash string already contains its salt and parameters, so only that string is stored.
- Login flow: rate limit → look up user → verify the Argon2 hash → check status is `active` → load role and permissions → create a session.
  - On failure, increment `failed_logins` and set status to `locked` once it reaches the threshold. Return the generic message "Login failed" and write a `LOGIN_FAILED` audit event.
- Admins can disable, enable or unlock users and change their role. Each of these writes an `ADMIN_ACTION` audit event.

### 5.2 Sessions (FR-04 to FR-07)
- The token is 32 random bytes. It goes into an `HttpOnly; Secure; SameSite=Strict` cookie, and the DB stores only its SHA-256 hash.
- `device_id` is a random UUID the frontend keeps in `localStorage` and sends at login. Logging in again from the same device replaces that device's session instead of using a second slot.
- **Two-device limit:** when a new device_id would make a 3rd active session:
  - `reject`: return "Maximum active sessions reached" and audit it. The user can revoke a device from the Sessions page on an existing device, and an admin can revoke any session.
  - `revoke_oldest`: revoke the oldest session, then create the new one.
- Every request checks `expires_at` (absolute lifetime) and `last_activity` (inactivity). An expired session is marked `expired`, the request gets 401, and the UI shows "Session expired. Please log in again".
- **Background message polling sends `X-Background: 1`, and those requests do not update `last_activity`.** Without this the inactivity timeout would never fire (issue P13).
- Revocation:
  - A user can revoke any of their own sessions.
  - An admin can revoke one session or all sessions for a user.
  - Logout revokes the current session.

### 5.3 Authorization (FR-08, FR-09)
- Every route checks, in order: authenticated → user active → has the required permission → owns the resource or is a recipient of it. A failure returns `403 Forbidden` and writes an `ACCESS_DENIED` audit event.
- File access is allowed only for the file's owner or a user it was shared with. Example: an HR user shares `hr_confidential.pdf` with HR colleagues. A Finance user who requests it gets 403. Meanwhile the Finance user can open the Finance report that was shared with them.

### 5.4 Company-only access (FR-10, FR-11, SR-05)
- `netguard` middleware runs first and checks the client IP against `TRUSTED_NETWORKS`.
  - If the IP is outside the trusted networks, the request is rejected with 403 and an `EXTERNAL_ACCESS_ATTEMPT` event is logged with source IP, timestamp, path, method and `BLOCKED`.
  - Application login is still required inside the trusted network, so network location alone never grants access.
- Uvicorn binds only to the LAN interface. The OS firewall should also restrict port 8443 (this is a deployment step, not code).
- The rate limiter is an in-memory sliding window per IP. Requests over the limit get 429 and a `RATE_LIMITED` audit event.
- `GET /health` is a health check that reports DB status.

### 5.5 Text messaging (FR-12)
- Sending uses `POST /api/messages` and requires `send_message`. The recipient must be an active user. The body is encrypted at rest with AES-GCM.
- Reading uses `GET /api/messages?with=<user>`. Fetching a conversation sets messages to `delivered`, and opening it sets them to `read`.
- Each message has a sender, recipient, timestamp, content and delivery status. The UI polls every 5 s with no WebSockets.

### 5.6 File upload pipeline (FR-13 to FR-20, §33 "Share file")
`POST /api/files` (multipart: file, client_sha256, recipients[]), with steps in this order:
1. **Authorization:** the uploader needs `upload_file` and `share_file`, and every recipient must be an active user.
2. **Extension:** the extension must be in `allowed_file_types` and enabled.
3. **MIME:** the declared `Content-Type` must equal the MIME expected for that extension.
4. **Magic bytes:** a hand-written signature table in `filecheck.py` gives `detected_type`, which must match the extension:
   - PDF `%PDF-`, PNG `89 50 4E 47 0D 0A 1A 0A`, JPEG `FF D8 FF`, WEBP `RIFF....WEBP`.
   - DOCX, XLSX and PPTX all start with the ZIP header `PK\x03\x04`. They are told apart by checking for `word/`, `xl/` or `ppt/` with the stdlib `zipfile`.
   - TXT has no signature, so it must decode as UTF-8 and contain no NUL bytes.
5. **Size:** `<= MAX_UPLOAD_MB`.
6. **Compatibility:** the type's `browser_compatible` flag must be set.
7. **Hash:** compute SHA-256 on the server and compare it with `client_sha256` from WebCrypto. A mismatch means the upload was corrupted in transit, so the file is rejected and an `INTEGRITY_FAILURE` event is logged.
8. **Encrypt:** AES-256-GCM with a fresh 12-byte nonce and AAD = `file_id`, so a blob can't be swapped onto another file record. The blob is written to `storage/<file_id>.bin` as `nonce || ciphertext || tag`.
9. Insert the `files` row and one `shares` row per recipient, then write `FILE_UPLOAD` and `FILE_SHARE` audit events.

If any of steps 2 to 6 fails, the file is rejected with a specific reason, for example "File rejected: Signature does not match declared type". An `INVALID_FILE_TYPE` event is logged and nothing is stored.

### 5.7 Download and integrity verification (FR-20, FR-21, SR-02, §33 "Receive file")
`GET /api/files/{id}`:
1. Check the session, then the permission and owner/recipient access.
2. Decrypt with AES-GCM. A tag failure means the blob or AAD was tampered with.
3. Recompute SHA-256 and compare it with the stored hash.
4. On any failure: set the file status to `integrity_failed`, write an `INTEGRITY_FAILURE` event, and return "Integrity verification failed. File unavailable. Security event recorded".
5. On success: return the file with an `X-File-SHA256` header and write a `FILE_DOWNLOAD` event.
6. **The browser hashes the received bytes with WebCrypto** and compares the result with the header:
   - Match: the UI shows "Integrity Verified ✓".
   - Mismatch: the UI calls `POST /api/files/{id}/integrity-report`, which is audited.
7. Images (JPG, PNG, WEBP) appear inline from a blob URL after verification, as required by the "image preview" item in §31. All other files are downloaded.
8. If the network fails mid-transfer, the UI shows "Transfer interrupted" with a **Retry** button.

### 5.8 Audit logging (FR-22, SR-04)
- `audit.log_event(user, device, event_type, resource, request_type, ip, result, details)`.
- Event types: LOGIN, LOGIN_FAILED, LOGOUT, SESSION_CREATED, SESSION_TERMINATED, SESSION_EXPIRED, FILE_UPLOAD, FILE_DOWNLOAD, FILE_SHARE, ACCESS_DENIED, INTEGRITY_FAILURE, INVALID_FILE_TYPE, EXTERNAL_ACCESS_ATTEMPT, RATE_LIMITED, ADMIN_ACTION.
- Audit records never store file contents, message text or passwords.
- Admins can view the log at `GET /api/admin/audit`, filtered by user, event type and date.

### 5.9 Administration (§5.1)
Admins can do all of the following:
- create, disable or unlock users
- create roles and edit their permissions
- enable or disable file types (only among types the code has signatures for, see issue P10)
- list and revoke sessions
- view the audit log and the security dashboard

### 5.10 Security dashboard (§21)
`GET /api/admin/dashboard` runs COUNT queries over a single DB:
- **Users:** active users, active sessions, locked or disabled accounts
- **Sessions:** current sessions, device count, expired sessions
- **Files:** uploads, downloads, rejected files, integrity failures
- **Network:** packets analyzed, connections, failed connections, suspicious events (from the latest or a selected capture)
- **Security:** failed logins, unauthorized requests, external access attempts, and the security events list

It is shown as plain tiles and tables with no chart library.

### 5.11 PCAP → SQLite pipeline (FR-23, FR-24, §34)
```bash
python analysis/pcap_to_sqlite.py capture.pcapng --db backend/data/securelink.db \
       --label after-tls [--keylog sslkeys.log]
```
1. Open the capture with `pyshark.FileCapture`, using a display filter on the intranet host and port.
2. For each packet, extract timestamp, src/dst IP, protocol (highest layer), src/dst port, length, TCP flags and `tcp.stream`.
3. Batch-insert the packets into `network_packets` under a new `captures` row.
4. Compute capture stats:
   - packets
   - connections (distinct streams)
   - failed connections (RST, or a SYN with no SYN-ACK)
   - **plaintext exposure:** packets where HTTP form or JSON content containing `password`, or file bytes, is visible. This number is the before/after evidence for FR-25.
   - **packet overhead:** bytes on the wire divided by application payload bytes.

### 5.12 Traffic detection (FR-26)
`analysis/detect.py <capture_id>` applies rules with configurable thresholds:

| Rule | Logic |
|---|---|
| Repeated failed connections | ≥ N RST or unanswered SYN from one source IP in 60 s |
| Abnormally high request rate | > N new connections per source IP in 10 s |
| Unexpected protocol | highest-layer protocol not in the expected set (TCP/TLS/HTTP/DNS/ARP) |
| Unexpected port | destination port on the server ≠ the app port |
| Large traffic burst | bytes per source IP per second > threshold |
| Repeated authentication failures | ≥ N HTTP 401s on `/api/auth/login` per client. Needs a plaintext capture or a TLS keylog (issue P17). The dashboard also shows the `LOGIN_FAILED` audit count. |

Each rule match writes a `security_events` row and raises `risk_score` (0 to 100) on the packets involved.

### 5.13 Wireshark before/after demonstration (FR-23, FR-25)
1. Run the server with `TLS_ENABLED=false` on an isolated lab network. Capture login, messaging, upload, download, a failed login and a 403 attempt. In Wireshark, show the password and file contents in plaintext.
2. Run the same steps with TLS. In Wireshark, only TLS records, IPs and ports are visible.
3. Import both captures with `pcap_to_sqlite.py` and compare their exposure counts and overhead.
4. Capture from the **phone to the server over Wi-Fi**. On Windows, loopback traffic needs the Npcap loopback adapter, so a phone client gives the most realistic capture.

### 5.14 Evaluation layer (§23 to §30)
**`evaluation/image_metrics.py <image>`** runs the image through the system's own `crypto.py` and prints a table:
- **Entropy:** Shannon entropy of the original bytes vs the ciphertext bytes (ciphertext should be close to 8 bits/byte).
- **MSE and PSNR:** original pixels vs pixels after decrypting. The expected result is MSE = 0 and PSNR = ∞, which is reported as "∞ (lossless)" (issue P3).
- **Correlation coefficient:** horizontal, vertical and diagonal adjacent pixels in the original vs the ciphertext reshaped to the image's dimensions.
- **NPCR and UACI:** C1 is the original encrypted, C2 is a one-pixel-modified image encrypted. Both use the product's real fresh-nonce encryption, and the caveat is documented (issue P2).

**`evaluation/benchmark.py --server https://...`** runs at 10 KB, 100 KB, 1 MB, 10 MB, 50 MB and 100 MB and writes CSV:
- Login response time and session creation time.
- Hashing, encryption, decryption and verification time, measured by calling `crypto.py` directly.
- Upload time, download time, end-to-end message latency, and throughput (MB/s).
- Server CPU % and memory, sampled with `psutil` on the server PID during the run.
- Packet overhead, taken from a PCAP of the benchmark run processed by `pcap_to_sqlite.py`.

The test files are synthetic PDFs (`%PDF-` header plus random body plus `%%EOF`) so they pass validation.

## 9. Issues found in the PRD and synopsis

### PRD (`prd.txt`)
| # | Section | Issue | Resolution in this plan |
|---|---|---|---|
| P1 | §24 | Leftover drafting note: *"Assuming 'NICR' refers to NPCR"*. The metric name was never confirmed. | Treated as NPCR. Remove the note from the final document. |
| P2 | §24–26 | NPCR, UACI and correlation are image-encryption metrics, and they **don't meaningfully evaluate AES-GCM**. With a fresh random nonce (the correct, secure use), C1 and C2 differ about 99.6% no matter what the plaintext change was, so the number measures nonce randomness rather than plaintext sensitivity. With a reused nonce (insecure), CTR mode changes only the one edited byte, so NPCR is about 0%. The 28-byte nonce+tag also stops the ciphertext from fitting the image's dimensions exactly. | Implement the metrics as required, run them on the real product encryption, and state the caveat in the report. Never reuse nonces. |
| P3 | §28 | "PSNR → very high". For a lossless pipeline MSE = 0, so PSNR = 10·log10(MAX²/0) is **infinite** (division by zero). MSE/PSNR also add nothing once SHA-256 equality is proven. | Report "∞ (lossless)" and present it as a sanity check. |
| P4 | §6 diagram | Traffic Capture is drawn hanging off the User Database. Capture actually happens at the network interface, not the DB. | Fix the diagram in the report. |

### Issues found while building
| # | Issue | Resolution |
|---|---|---|
| B1 | Browsers expose WebCrypto (`crypto.subtle`, `randomUUID`) only on HTTPS or localhost, so the FR-25 "before" experiment over plain HTTP could not hash files or create device IDs. | Device IDs use `getRandomValues`. In lab plaintext mode only, the client sends `unavailable` and the server skips the client-hash comparison (the server-side checks still run). HTTPS mode rejects `unavailable`. |
| B2 | Some mobile browsers send an empty or `application/octet-stream` Content-Type for Office files, which would fail a strict FR-16 MIME check. | A generic declared MIME is tolerated, but the MIME derived from the magic bytes must still equal the expected MIME. |
| B3 | FastAPI runs yield-dependency cleanup after the response is sent, so a commit there let the next request read stale data (for example, a revoked session still worked for a moment). | SQLite autocommit, with explicit transactions for multi-row writes. |
| B4 | On Windows, `localhost` resolves to IPv6 first. The server listens on IPv4, so each new connection waits about 2 s, which inflates the login timings. | Use the IP address in scripts and benchmarks (documented in the README). |
| B6 | Tabs of one browser share the session cookie. After a logout and login as another user in tab B, tab A kept showing the old user's header and tabs while its requests ran as the new user (found in user testing). | Login and logout broadcast through a `localStorage` key. Other tabs reload `/api/auth/me` and remount their views, or show "You were logged out in another tab". |
| B7 | On Windows, Uvicorn's default asyncio Proactor loop logs `ConnectionResetError [WinError 10054]` tracebacks whenever Chrome resets an idle keep-alive connection: `_call_connection_lost` calls `socket.shutdown()` without a try/except. Requests are unaffected, but the logs look alarming. | `backend/run.py` selects `asyncio:SelectorEventLoop` on Windows. Smoke test still all OK; no tracebacks. |
| B5 | Wireshark on Windows can't capture without Npcap, and traffic from the server PC to itself never reaches the Wi-Fi adapter. | Install Npcap. Use separate client devices, or the Npcap loopback adapter with `--server-ip 127.0.0.1`. |
